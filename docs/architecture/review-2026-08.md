# 架构审查报告（2026-08）

> 审查方法：通读 `DESIGN.md` / `docs/architecture/*` 后，逐一核对核心代码路径——启动序列（`SnapshotApp`）、Root 服务接入（`ProvidersImpl` / `IServiceClient` / `FileSystemProviderImpl`）、压缩管线（`ZstdCompressor` / `FileSystemImpl` / `io-tar` JNI）、快照创建（`ArchiveMaker` / `SnapshotCreator`）、恢复（`ArchiveRestorer` / `DataRestorer`）、全局状态（`AppDataRepository` / `SnapshotViewModel`）与配置（`GlobalConfig` / `GroupConfig`）。
>
> 本文是**评估性**文档，描述性架构请看[架构总览](overview.md)。每项发现标注问题类与优先级：P1（正确性/契约）、P2（结构性债）、P3（可维护性）。

---

## 总体评价

架构骨架是健康的：模块划分（契约 `api` / 实现 `provider` / 原生 `io-*` / 辅助 `hiddenapi`+`systemapi`）边界清晰、依赖方向正确；原生管线（root 进程内 fork+GNU tar → FIFO → zstd 多线程流式压缩）设计精巧且符合"原生性能优先"的设计哲学；文档体系完整度远超同规模项目。

主要债务集中在四处：**任务契约（`ITaskHandler`）名存实亡**、**恢复流程绕过 Root 服务边界直接在 app 进程执行 root shell**、**错误在各层被吞掉后以布尔值/null 传播**、以及**数据项类型分派逻辑的散弹式重复**。这些不是孤立 bug，而是会持续产生同类问题的结构缺口。

## 实际运行时拓扑（与文档描述的差异）

审查中确认的实际进程分布，与 `overview.md` 分层图的直觉略有出入：

```
App 进程（普通权限 + 持有 root main shell）        Root 进程
──────────────────────────────────────           ─────────────────
FileSystemImpl / FileCompressor                  SnapshotRootService
ZstdCompressor / ZstdDecompressor  ← zstd 在这里    ├─ 4 个领域 Handler
FlowableStreamParallelCopier                        └─ callTarCli → fork + GNU tar
SELinuxShell (chown/chcon via su)  ← 第三条 root 通道
                                                 FileSystemManagerRootService
                                                    └─ libsu-nio 文件 I/O
```

三个关键事实：

1. **zstd 压缩/解压的 CPU 工作发生在 app 进程**，不在 root 进程。`FileSystemImpl` 及其 `FileCompressor` 由 `FileSystemProviderImpl.provide()` 在 app 进程构造；tar（root 进程）经 FIFO 把字节流交给 app 进程的 `ZstdOutputStream`。`overview.md` 把 `FileCompressor → Zstd/Tar` 画在"Root 服务层"下，模块归属没错（`:provider`），但**进程归属**容易被误读。
2. **Root 通道实际有三条**，而非文档所述两条：AIDL 主服务、libsu-nio 文件服务，以及 **app 进程内直接持有的 root main shell**（`AppShell.initMainShell` 以 `su` + mount master + 全局挂载命名空间初始化，`SELinuxShell`/`PmShell` 经它执行）。
3. `IFileCompressor` 虽是 AIDL Stub，但**始终在进程内调用**——当前并没有跨进程的压缩回调。AIDL 形态是为未来迁移预留的，成本是 Binder 线程语义的假象（见发现 2）。

## 主要优势

- **依赖方向严格单向**：`app → {api, provider, hiddenapi}`，`provider → {api, hiddenapi, systemapi, io-*}`，`api` 不依赖任何内部模块。经 build.gradle.kts 逐一核实，无环。
- **原生层质量高**：`io-tar/jni.cpp` 的 fork 子进程处理了 `PR_SET_PDEATHSIG`、fd 卫生（dup2 后关闭闲置 fd）、退出码回传；FIFO 流式管线消除了中间文件，与 DESIGN.md 承诺一致。
- **Handler 模式分域清晰**：`SnapshotRootService` 按应用管理/权限/SSAID/文件系统四域拆分 Handler，AIDL 表面 30+ 方法但实现各归其位。
- **近期代码质量明显优于早期**：`main/launch/batch/`（批量恢复）与 `timeline/` 有职责拆分（Planner / Resolver / RecordStore）和配套单元测试，是后续重构其余部分的样板。
- **文档体系**：两层文档（knowledge/action）+ frontmatter 规范 + 术语表，AGENTS.md 记录了关键不变量（如 viewModelScope 陷阱）。

## 发现的问题

### 1. P1 · 契约漂移：`ITaskHandler.cancel()` 从未接线，取消真相已扩散为多套

**问题类**：契约漂移 / 单一真相源缺失。

**现状**：`ITaskHandler` 是 AIDL 契约，声明 `start/cancel/state/id`。但全仓库没有任何调用方调用 `cancel()`；`ZstdCompressor.compress()` 返回的 handler 里 `isCancel` 置位后**从未被读取**（`ZstdCompressor.kt:49,65` 设置，压缩循环从不检查）。真正的取消是调用方各自的 `AtomicBoolean`，且**扩散已是现在时**，不止 `SnapshotCreator.isCanceled`（`SnapshotCreator.kt:122-125`）一处：`GroupBatchArchiver`、`GroupBatchRestorer`、`TimelineBatchOperator` 各自维护 `isCancelled + isForceCancelled` 成对标志（`TimelineBatchOperator.kt:52-53,160-161,286-287` 等共 5 处）。这些标志都只能**跳过尚未开始的任务**——正在压缩的大文件无法中断，用户点取消后仍要等当前项跑完。

**复发机制**：取消语义分散在"契约声明（未实现）"与"调用方私有标志（粒度粗）"两处，每个新批量路径都会再发明一套标志——已发生三次。

**建议**：与发现 2 一并做**契约重写**（二选一），而非仅仅接线 `isCancel`：
- 方案 A（推荐，与现状匹配）：承认同步语义——契约改为同步返回结果（`suspend`/阻塞函数 + 结构化取消），删除 `state()` 轮询与 `cancel()`；取消经协程 `Job.cancel()` 传播，`FlowableStreamParallelCopier` 已支持中断（`ZstdDecompressor.kt:208` 证明可行）。
- 方案 B：真正异步化——`start()` 立即返回，内部起协程，`cancel()` 接到复制器；调用方只持有 handler，禁止再造私有标志（配 review/Detekt 规则）。

### 2. P1 · 契约不变量缺失：压缩侧状态机名存实亡

**问题类**：契约无强制不变量。

**现状**：`ITaskHandler` 的形态暗示异步任务（有 `state()` 状态机），但所有实现的 `start()` 都是**同步阻塞**的（`ZstdCompressor.doCompress` / `ZstdDecompressor.doDecompress` 内部 `runBlocking`）。更严重的是压缩与解压行为不一致：
- **解压侧**（`ZstdDecompressor`）会把状态推进到 `COMPLETE`/`ERROR` 终态，因此 `DataRestorer.kt:87-91` 的轮询虽是死逻辑（`start()` 返回时状态已终结，最多转一圈）但结果正确；
- **压缩侧**（`ZstdCompressor` 含 multiple 版本）`start()` 只置 `RUNNING`，**从不置终态**。这意味着 `SnapshotCreator.kt:134` 的 `state() == COMPRESS_STATE_ERROR` 失败检查对所有 zstd 压缩任务**永远为假**——压缩失败不会触发该分支的存档目录清理，错误只能靠 `callback.onError` 更新对话框，快照目录残留半成品。

**复发机制**：契约没有写明"start() 是否阻塞、状态必须收敛到终态"这两条不变量，每个实现和调用方各自理解。

**建议**：随发现 1 的契约重写一并消除：同步 Result 方案下 `state()` 整个删除；若保留状态机，必须在契约层写明"start() 返回时 state 必为终态"并让压缩侧补齐——但前者更不易再漂移。

### 3. P1 · 边界泄漏：恢复流程在 app 层直接执行 root shell

**问题类**：边界泄漏 / 职责错位。

**现状**：`DataRestorer`（`:app` 模块）直接 import `provider.root.SELinuxShell`，在 app 进程通过 libsu main shell 以 root 执行 `chown -hR` / `chcon -hR`（`DataRestorer.kt:49,106,111`）。`AppInfo.kt:12` 也直接引用 `provider.utils.drawableToBitmap`。这违反了两条明文规则：
- AGENTS.md："app 模块通过 `Providers` 接口访问 root 服务——绝不直接接触 root 内部"；
- DESIGN.md："Root 操作通过 AIDL 接口暴露，仅包含预定义方法"。

恢复正确性的关键一环（属主/SELinux 上下文还原）落在了设计上"不该有 root 逻辑"的层里，且走的是第三条 root 通道（shell 字符串拼接，路径仅双引号包裹、未转义 `$`/反引号——路径来源是包名与配置，实际注入风险低，但契约上无保障）。

注意：root 侧**并非完全没有属主 API**——`FileSystemHandler` 已有非递归的 `setUid`/`setGid`/`getUid`/`getGid`（基于 `Os.chown`/`Os.stat`）。缺口是**递归 chown 与 SELinux getcon/chcon**，即"补全并正式化既有能力"，不是从零新造。

**复发机制**：根因不是某个 import，而是 **`:provider` 同时承载两种进程角色**——app 进程侧实现（`ProvidersImpl`/`FileSystemImpl`/`*Compressor`）与 root 进程侧服务（`*RootService`/`handler`/`root.*`）混在同一模块，`app → provider` 的 Gradle 依赖使"不碰 root 内部"无法靠模块边界成立。只要 app 进程的 root main shell 存在且 provider 内部包可见，任何"AIDL 里还没有的 root 操作"都会走捷径直接 shell。

**建议**：
1. 短期：把递归 chown、`getcon/chcon` 提升为 `IFileSystem`（或 `ISnapShotRootService`）的正式方法，在 root 进程实现；`:app` 对 `provider.root.*`、`provider.utils.*` 的 import 清零。
2. 结构性：按**进程角色**切分 `:provider`——client 侧与 root-service 侧分包（或分模块），client 侧只暴露 `ProvidersImpl` 入口，其余 `internal`；配 Detekt/Gradle 机械检查（禁 `app` 引用 root 侧包、禁新增 `Shell.cmd` 调用点）。机械规则守的是"进程角色"这条不变量，而非逐个 import。

### 4. P2 · `api` 模块包含完整实现：`IServiceClient`

**问题类**：错误分层。

**现状**：`api/src/.../IServiceClient.java` 是约 450 行的服务绑定基础设施（线程池、`CompletableFuture`、DeathRecipient、重绑定逻辑），却放在"必须只有接口和数据类"（AGENTS.md 明文约定）的 `:api` 模块里。

**建议**：迁到 `:provider`（或新的 `:ipc-client` 基础模块）。`api` 中只留 `IServiceRemoteObserver` 这类回调接口。顺带审查：`waitFetch` 的超时兜底（`IServiceClient.java:246-254`）掩盖了"绑定慢 vs 绑定死"的区别，迁移时值得加上失败原因的区分。

### 5. P2 · 域对象携带服务引用：`AppInfo`

**问题类**：边界泄漏 / 可测试性。

**现状**：`app` 模块的 `AppInfo` 是 data class，但构造参数里带着 `fs: IFileSystem` 和 `appManager: IAppManager`（`AppInfo.kt:20-27`）。后果：
- data class 的 `equals/hashCode` 把服务代理算进相等性，语义错误（两个逻辑相同的 AppInfo 可能不等）；
- 域对象无法脱离运行中的 root 连接构造，相关逻辑（过滤、排序、Xposed 检测）难以单测；
- 与 `api` 模块的 Parcelable `AppInfo` 同名不同物，读代码时易混淆。

**建议**：`AppInfo` 退化为纯数据（包名、userId、版本、flags、路径），需要服务的操作移到 repository/helper 层按需传入。`SnapGroup` 同理——它同时承担配置访问、目录扫描、图标落盘、`.nomedia` 管理（`SnapGroup.kt:78-155`），扫描/装载逻辑应归 `AppDataRepository` 或专职 loader。

### 6. P2 · 共享可变集合的锁纪律不完整

**问题类**：并发 / 缺少不变量。

**现状**：`SnapGroup.apps` 是 `mutableListOf`，`loadApps` 内用 `synchronized(apps)` 保护写入，但**把 `apps` 直接 return 给外部**（`SnapGroup.kt:153`），UI 适配器在无锁状态下遍历它，后台 reload 同时 `clear()` 会产生 `ConcurrentModificationException` 或渲染半旧数据。`ArchivedApp.archives` 有同样模式（`ArchiveManager.kt:62` 有锁，其它读点无锁）。

**建议**：装载函数返回**不可变快照**（`toList()`），集合本身 private；或整体改为"重建后整表 postValue"的不可变数据流（`AppDataRepository.reloadGroupsLocked` 已经是这个方向，把组内 apps 也纳入即可）。这能把"锁纪律"从每个调用点的自觉，变成类型系统强制。

### 7. P1 · 错误被吞：布尔值/null 掩盖根因

**问题类**：失败处理错层。

**现状**：错误路径几乎全是 `catch (e) { printStackTrace(); return false/null/-1 }`：
- `ArchiveMaker.makeSnapshot` 任何异常 → 返回 null → 用户只看到 "no task"（`ArchiveMaker.kt:335-338`，`SnapshotCreator.kt:155`）；
- `FileSystemHandler` 的 root 侧方法用 `runCatching{}.getOrNull() ?: false`，root 进程内的失败原因（权限、SELinux、路径不存在）不过 Binder 就地蒸发；
- `ICompressCallback.onError(String)` 只传消息字符串，错误类别（可重试/致命/用户可修复）无法区分。

**复发机制**：契约层没有错误通道，每层只能各自吞掉或转成布尔值，排查设备端问题时只剩 logcat 考古。

**建议**：不必引入重型 Result 框架，两步即可：
1. AIDL/接口边界给失败留结构化通道——`onError(code: Int, msg: String)` 或返回带 `errno` 语义的负值约定，root 侧 `FileSystemHandler` 把异常类型映射成错误码；
2. 层内保持异常，**只在边界处显式转换**，禁止中途 `getOrNull()`。可在 code review 清单里加"新代码禁止无日志吞异常"。

### 8. P1 · FIFO 管线缺少看门狗：单侧失败可致永久挂起

**问题类**：失败与生命周期。

**现状**：压缩管线依赖 FIFO 的阻塞语义（写端等读端，反之亦然）。`streamCompress` 起三个并发任务（tar 写 stdout FIFO、读 stderr FIFO、zstd 读 stdout FIFO），若 tar 在 open FIFO 前崩溃（或反之），对端的 `open()` 将**无限阻塞**——`coroutineScope` 等不到子任务结束，任务永久挂起且无超时。`streamCompressMultiple` 的 60s "看门狗"（`ZstdCompressor.kt:446-456`）实际是**无效检查**：它轮询 `fileSystem.exists(stdOut)`，而该 FIFO 在进入协程前就已 `mkfifo` 创建（`ZstdCompressor.kt:396-399`），条件立即为真，检查形同虚设——它验证的是"文件存在"，需要验证的是"对端已打开"。单文件版本连这个空检查都没有。另外 stderr FIFO 读取在 tar 从不打开 stderr 时同样会卡住。

**建议**：给管线加真实的看门狗——`withTimeout` 包住 open 阶段（open 成功与否才是"对端就绪"的信号），tar 退出码返回后主动以非阻塞方式打开/关闭残留 FIFO 解除对端阻塞；删除现有的 exists 假检查。实现上收敛为一个小的内部 helper（tar→zstd 与 zstd→tar 两条管线共用超时 + 解除阻塞逻辑即可，不必预先抽象成框架），而不是每个压缩器各写一遍。挂起属正确性问题，列 P1。

### 9. P3 · 数据项类型的散弹式分派

**问题类**：缺少单一入口的重复逻辑。

**现状**：新增一种数据项（假设 `cache`）需要同步修改至少 4 处近似复制的代码：
- `ArchiveMaker.makeSnapshot` 的 when 分支（data/user/user_de/obb/media 五段几乎逐字重复，`ArchiveMaker.kt:180-325`）；
- `ArchiveRestorer.restoreDataItem` 的 when 分支（`ArchiveRestorer.kt:511-567`）;
- `CompressItems` 常量与文件命名约定；
- 恢复目标路径映射（`AppInfo.getXxxDir()` 系列）。

`ZstdCompressor.streamCompress` 与 `streamCompressMultiple`、`ArchiveRestorer.restoreArchive` 与 `restoreArchiveWithSelectedTypes` 也是成对的近似复制。

**建议**：引入数据项描述表——`ItemSpec(name, sourcePathOf(appInfo), targetPathOf(appInfo), excludeKey, needsChown)` 的注册表，打包/恢复循环遍历表驱动执行。这是典型的"表驱动 + 策略"收益场景：五段 when 合并为一段，新增类型只加一行注册。同时 `makeSnapshot` 可拆成纯函数的"计划构建"（可单测）与"任务执行"两相。

## 安全面观察

1. **`callTarCli` 是宽 root 原语**：AIDL 允许调用方传任意 tar argv，而 GNU tar 支持 `--to-command=CMD`（对每个成员执行任意命令）。因此"仅预定义方法、无任意命令执行"（DESIGN.md）在严格意义上不成立——`callTarCli` 等价于受限的 root 命令执行入口。**缓解因素**：libsu `RootService` 只能被本应用绑定，攻击面仅限本进程内代码。建议：在 root 侧对 argv 做白名单校验（只允许 `-c/-x/-p/-f/-C/--exclude/-X`），把"无任意命令执行"变成被强制的不变量而非口头承诺。
2. **app 进程常驻 root main shell**（发现 3 的另一面）：即使收敛 SELinuxShell，`Shell.getShell()` 的 root 会话仍在 app 进程可用。若目标是"UI 层无 root"，需要盘点所有 `Shell.cmd` 调用点并逐步下沉。
3. **快照明文平铺在共享存储**：这是 DESIGN.md 的自觉取舍（Syncthing 透明同步），但意味着任何持有 `MANAGE_EXTERNAL_STORAGE` 的应用可读取被备份应用的全部数据。[安全策略](cross-cutting/security.md) 应向用户显式披露此边界。

## 可测试性

## 建议路线（按优先级）

1. **P1 契约重写**（发现 1、2、7）：`ITaskHandler` 语义二选一（同步 Result 或真异步 Job）+ 状态终态不变量 + 错误码通道，配 ADR 冻结语义，并加"禁止业务层私有取消标志"的 review/Detekt 规则。
2. **P1 FIFO 看门狗**（发现 8）：open 超时 + 单侧失败解除对端阻塞，删除 exists 假检查。挂起属正确性问题，与契约修复同批。
3. **P1 边界收口**（发现 3 + 安全 1）：递归 chown/SELinux 操作正式化下沉 root 服务、`callTarCli` argv 白名单、`:provider` 按进程角色分包并机械检查（含盘点 `Shell.cmd` 调用点）。
4. **P2 生命周期加固**（杂项重连）：libsu-nio binder 死亡重连。
5. **P2 结构清理**（发现 5、6，发现 4 靠后）：`AppInfo`/`SnapGroup` 去服务引用、集合快照化；`IServiceClient` 迁出 api 属分层债、不影响用户正确性，排最后。
6. **P3 表驱动重构**（发现 9）：数据项注册表，随下一次新增数据项类型时顺势实施。

每步独立可交付，无相互阻塞；1–3 为正确性批次，建议先行。

## 非目标

本审查不建议：引入 DI 框架（Hilt/Koin——当前手工装配规模可控）、迁移 Compose（`DESIGN.md` 已记录该取舍，注意目前并无正式 ADR）、引入数据库（与"存储透明"哲学冲突）、为 AIDL 化的 `IFileCompressor` 强行跨进程（现进程内调用无实际问题）、重型 Result/错误框架（错误通道用错误码即可）。
