# r01 api 审查发现

通读 `api/src` 下 26 个源文件（`.java` / `.kt` / `.aidl`；无 `.cpp` / `.h`）。Parcelable 与 AIDL 的字段顺序一致，接口本身没有可执行分支。下面 5 条都来自 `IServiceClient` 的绑定生命周期。

## r01-1
- 严重度：中
- 症状：`releaseClient` 返回后，这次 `bindService` 仍留在系统里；`client` 被置空后再次 `fetchRemote` 会再绑上一份，旧连接的断连和死亡回调还在。
- 代码：`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:96-113`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:225-233`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:266-274`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:383-440`
- 为什么是问题：`fetchRemote` 用 `applicationContext` 调用 `bindRemote`。真正交给 `bindService` 的是方法内部新建的 `ServiceConnection`，返回值只做了 null 检查就丢掉。`releaseClient` 在 `client == null` 时直接 return，一次都不解绑。`client` 非空时走到 `unbindService`，解的是字段 `connection`。这个字段只被 wrapper 转发回调，没有传入 `bindService`。`Context.unbindService` 对未登记的连接抛 `IllegalArgumentException`，被 `doUnbind` 吃掉。入参 `Context` 也常常不是绑定用的 `applicationContext`，查找不到同一个 dispatcher。服务以 `BIND_AUTO_CREATE` 继续活着，下次 `isConnected()` 为 false 会再 `bindService` 一次。
- 方向：保存 `doBind` 返回的 `ServiceConnection` 和绑定用的 `Context`，释放时用同一对解绑。

## r01-2
- 严重度：中
- 症状：同一次连接会把死亡观察者通知两次；旧 binder 的死亡回调会把当时的 `client` 清掉，重连已经写上的新客户端也会被清掉。
- 代码：`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:212-214`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:227`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:277-292`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:301-321`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:394-411`
- 为什么是问题：`fetchRemote` 把字段 `connection` 传进 `bindRemote`。wrapper 在 `onServiceConnected` 里已经 `linkToDeath`、调用 `onConnected` 并 `complete`，随后又调用字段 `connection.onServiceConnected`，里面再 `linkToDeath` 和 `onConnected` 一次。同一个 `deathRecipient` 登记两次，进程死亡时 `binderDied` 进来两次，`onBinderDied` 对仍保留的观察者通知两次。`binderDied` 不比较死亡的是哪一个 binder，直接 `unlinkToDeath` 当前 `client` 并置空。`fetchRemote` 在未连接但 `client != null` 时只把字段改成 null，没有 `unlinkToDeath`，旧登记还在；这次回调晚于新的 `onServiceConnected` 时，新客户端被清掉。
- 方向：死亡回调只登记一次，并且只清除登记时的那个 binder。

## r01-3
- 严重度：中
- 症状：服务已经断开后，`waitFetch` 立刻返回上一轮的接口并调用 `onFetched`，调用方拿到的 binder 已经不可用。
- 代码：`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:216-218`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:243-245`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:280-291`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:334-337`
- 为什么是问题：首次连上之后 `clientFuture` 保持 completed。`binderDied` 和 `onServiceDisconnected` 只把 `client` 置空，不更换这个 future。`waitFetch` 不看 `isConnected()`，对已完成的 future `get` 会马上得到旧实例，接着 `onFetched` 并返回。只有 `fetchRemote` 在 `isDone()` 时才会换成新 future。断开之后若先进入 `waitFetch`，返回值是死 binder，后续远程调用失败。
- 方向：断开时作废旧 future，`waitFetch` 返回前确认 binder 仍然存活。

## r01-4
- 严重度：低
- 症状：等待在超时边界上已经连上时，返回值没有经过 `onFetched`；判定未连上时，方法仍把那个 `client` 交回去。
- 代码：`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:243-263`
- 为什么是问题：`get` 正常返回时会先 `onFetched` 再返回。`TimeoutException` 分支里，`cachedClient` 仍能 `pingBinder` 时直接 `return cachedClient`，没有 `onFetched`。ping 失败时日志写了未连接，然后落到方法末尾 `return client`，交回刚刚判定不可用的对象。`CancellationException` 和其它异常同样被吃掉后 `return client`。调用方只看返回值是否为 null，区分不出这次等待失败。
- 方向：超时后确认仍连接时同样调用 `onFetched`；失败时返回 null，不要交回已判死的 `client`。

## r01-5
- 严重度：低
- 症状：工作线程先进入 `waitFetch` 时，主线程进不了 `fetchRemote`，空等 `BIND_TIMEOUT` 秒后得到 null，绑定这才开始。
- 代码：`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:43-47`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:203-233`、`api/src/main/java/tiiehenry/android/snapshot/app/IServiceClient.java:237-243`
- 为什么是问题：`clientFuture` 一开始就是未完成的。`waitFetch` 整个方法 `synchronized`，在 `get(BIND_TIMEOUT, SECONDS)` 上最多阻塞 15 秒，期间一直占着实例锁。`fetchRemote` 也是 `synchronized`，这段时间无法执行 `bindService`，没有人能 `complete` 这个 future。超时后返回当时的 `client`，初始状态是 null。
- 方向：阻塞在 future 上时放开实例锁，让主线程能进入 `fetchRemote`。
